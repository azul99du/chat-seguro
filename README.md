# chat-seguro
Chat com criptografia ponta a ponta. Front estático (GitHub Pages) + Supabase.

## Como rodar
1. Crie um projeto no Supabase e rode `supabase/schema.sql` no SQL Editor.
2. Preencha `config.js` com a URL e a chave publishable.
3. Em Authentication > Providers > Email, desative "Confirm email" para testes.
4. Sirva a pasta: `python3 -m http.server 8000` e abra http://localhost:8000.

## Criptografia
ECDH P-256 (WebCrypto) -> AES-GCM 256. Chave privada no IndexedDB. O banco só vê chave pública, texto cifrado e o backup da chave privada cifrado por uma frase-senha (PBKDF2 600k + AES-GCM) que só o usuário sabe. Esqueceu a frase-senha em um aparelho novo = mensagens antigas perdidas.

## Mídia e privacidade
- Fotos: redesenhadas no canvas antes do envio (descarta EXIF, GPS, modelo, data), reduzidas a 1600 px. GIF vira imagem parada.
- Vídeos MP4/MOV (até 45 MB): o contêiner é limpo sem recodificar (título, GPS, datas, faixas de metadados). Resta só a assinatura do codificador dentro dos dados do vídeo.
- O arquivo é cifrado no navegador (AES-GCM, chave aleatória por arquivo) antes de ir para o Storage; a chave vai dentro da mensagem cifrada.
- Fundo de conversa: pessoal, limpo de metadados e cifrado.
- **Áudio:** grave pelo microfone (botão do microfone; até 5 min, com prévia antes de enviar) ou anexe MP3, M4A ou WAV (até 20 MB). MP3 perde ID3v2/ID3v1/APE (artista, título, capa, comentário); WAV guarda só `fmt`/`data` (some LIST/INFO, bext, iXML); M4A passa pela mesma limpeza do MP4 (GPS, data, título); a gravação do navegador (MP4/AAC ou WebM/Opus) tem aplicativo, título e data zerados e blocos Tags/Attachments/Chapters apagados. Tudo sem recodificar, no mesmo tamanho. O amigo baixa e decifra só ao tocar em "Ouvir áudio". Outros formatos (OGG, FLAC, AAC solto) são recusados com aviso.

## Pendente
- Trocar a frase-senha; trocar a senha de login (pede a atual, 12+ caracteres, derruba os outros aparelhos; com 2FA exige o código); revogar aparelhos.
- Verificação de chave (código de segurança) contra servidor malicioso.
- Considerar protocolo Signal/biblioteca auditada antes de uso sério.

## Segurança
- **CSP** no `index.html`: só roda código do próprio site e só fala com o Supabase do projeto. A biblioteca do Supabase fica em `vendor/supabase.js` (empacotada do npm `@supabase/supabase-js@2.45.4` com esbuild), sem CDN de terceiros.
- **Banco:** RLS em todas as tabelas; `anon` sem acesso a nada; o cliente só escreve destinatário + texto cifrado (não forja data nem "visto"); perfil visível só para quem já conversou (busca por nome exato via `find_user`); backup da chave privada em tabela própria.
- **Chaves:** código de segurança por conversa e alerta se a chave de um amigo mudar; frase-senha do backup com no mínimo 12 caracteres; "Sair e apagar chaves" para aparelhos compartilhados.
- **Mídia recebida nunca é confiável:** tipo restrito a imagem/vídeo, caminho validado, nunca `text/html`.
- **Fazer no painel do Supabase:** Realtime → desligar "Allow public access"; Authentication → considerar desligar novos cadastros depois que os amigos entrarem e ligar a confirmação de e-mail.

## Sigilo futuro (forward secrecy)
Mensagens novas usam **Double Ratchet** (como o Signal) com acordo de chaves 3DH: `ratchet.js` (protocolo, testável sem navegador), `store.js` (sessões e histórico cifrados no aparelho).
- Cada mensagem usa uma chave nova, derivada da anterior por função de mão única, e a chave antiga é apagada. Roubar a chave de identidade, o backup ou o estado de hoje não revela o passado.
- Cada vez que os dois trocam mensagens, uma chave DH nova entra na cadeia: quem teve a chave vazada deixa de acompanhar a conversa (autocura).
- O servidor guarda só texto cifrado + cabeçalho (id da sessão, chave DH da vez e contadores).
- **Consequência:** o histórico novo fica **só no aparelho** que enviou/recebeu (cifrado com chave local). Em aparelho novo, mensagens antigas com sigilo futuro aparecem como "não disponíveis"; as mensagens do formato antigo (v1) continuam legíveis em qualquer aparelho. Se um amigo trocar de aparelho, a sessão é refeita sozinha.
- Limites: sem chaves de uso único, as primeiras mensagens de uma sessão ficam expostas enquanto a chave de médio prazo (SPK, 7 dias + 14 de carência) existir. Com vários aparelhos na mesma conta, cada mensagem a dois é cifrada para cada aparelho (veja "Vários aparelhos na mesma conta: etapa 2"); só os grupos ainda vão para um aparelho por pessoa.

## Testes
```bash
npm ci
npm run test:unit   # protocolo de sigilo futuro, limpeza de vídeo, cifra de arquivo, código e schema (precisa de ffmpeg)
npm run test:e2e    # navegador + banco, contra um projeto Supabase DE TESTE (veja abaixo)
```
- **`tests/ratchet.test.mjs`**: sessão, ordem trocada, repetição, adulteração, redirecionamento, troca de chave de médio prazo, vazamento total do estado (passado não abre) e autocura.
- **`tests/media.test.mjs`**: vídeos MP4/MOV com título, GPS, data e faixa de timecode saem limpos, do mesmo tamanho, e continuam tocando; cifra de arquivo.
- **`tests/static.test.mjs`**: sem `innerHTML`/`eval`, sem scripts de CDN, sem chave secreta, CSP correta, RLS ligado em toda tabela, funções `SECURITY DEFINER` seguras.
- **`tests/e2e/security.test.mjs`**: ataques com conta comum e sem login (ler, forjar, mover reações, prekeys alheias, storage). Tudo precisa ser bloqueado.
- **`tests/e2e/flow.test.mjs`**: duas pessoas no Chromium: mensagens em tempo real, reações, foto e vídeo, fundo, recarregar, duas abas, aparelho novo, alerta de troca de chave.

### Projeto de teste (para o `test:e2e`)
Os testes criam contas e mensagens de verdade, então **nunca** rodam contra o banco real: `SUPABASE_URL` igual ao de `config.js` é recusado (a trava só se desliga com `ALLOW_PROD=1`).
1. Crie um projeto Supabase só para testes e aplique `supabase/schema.sql` (o schema recria exatamente o banco real; já foi conferido catálogo a catálogo).
2. No painel desse projeto, em **Authentication → Providers → Email**, desligue **Confirm email**. Sem isso o cadastro de teste não devolve sessão e os testes se pulam com um aviso.
3. `SUPABASE_URL=... SUPABASE_KEY=<chave publishable> npm run test:e2e` (use `CHROMIUM_PATH` para apontar um Chromium já instalado).
No GitHub Actions (`.github/workflows/ci.yml`) a ponta a ponta **não usa um projeto hospedado**: cada um de 8 grupos de testes (divididos por `scripts/e2e-grupo.mjs`) sobe o **seu próprio Supabase local e descartável** (Supabase CLI + Docker, configurado em `supabase/config.toml`), aplica `supabase/schema.sql` do zero (então o próprio schema é testado a cada rodada) e roda ao mesmo tempo que os outros 7. Só os 2 arquivos que usam as Edge Functions (`aparelhos` e `notificacoes`, que o banco local não tem) rodam num job curto no projeto de teste hospedado `chat-seguro-teste`, um de cada vez. Resultado: uns **5 minutos** em vez de 27 a 30. Para rodar um grupo localmente: `supabase start`, aplicar o schema, `SUPABASE_URL=http://127.0.0.1:54321 SUPABASE_KEY=<chave do supabase status> node --test $(node scripts/e2e-grupo.mjs 1 8 --sem-funcoes)` (o endereço sem https só é aceito para 127.0.0.1).
O Realtime do Supabase não garante entregar todo aviso (no banco local isso aparecia a cada poucas rodadas), então o app também **confere o servidor a cada 30 s com a tela à vista**, sempre que o canal reconecta e de novo se a busca falhar; nos testes esse intervalo é de 3 a 4 s (`lacre:poll` no armazenamento do navegador; `0` desliga). Teste: `tests/e2e/chegada.test.mjs` (sem tempo real nenhum, a mensagem chega mesmo assim).

## Limites de uso e monitoramento
**Limites no banco** (todos devolvem HTTP 429 "espere um pouco"; o site mostra uma mensagem clara):
- mensagens: 300 por minuto e 5000 por hora por pessoa, contando MENSAGENS (um pedido = uma mensagem, tenha quantas linhas tiver: uma por aparelho de cada destinatário); as linhas têm teto próprio de 3000 por minuto e 30000 por hora; no máximo 100 linhas por pedido (grupo de 20 pessoas com 5 aparelhos cada = 99; reações e controle contam);
- grupos: criar 5 por minuto e 20 por hora; adicionar/remover/renomear/dar cargo/trocar foto 30 por minuto e 200 por hora; no máximo 20 pessoas por grupo e 50 grupos por pessoa;
- busca de amigo (`find_user`): 15 por minuto e 100 por hora; busca de chave (`get_prekey`): 30 por minuto e 300 por hora;
- chaves de médio prazo: no máximo 30 por pessoa e 5 por pedido;
- arquivos: 200 por hora e 400 MB no total por pessoa.

**Monitoramento:** `supabase/monitoramento.sql` tem consultas prontas (contas novas, quem manda muito, quem bate nos limites, armazenamento, último acesso). Os logs de acesso (países/redes, erros 4xx/5xx, falhas de login) ficam em *Logs* no painel do Supabase e podem ser consultados por aqui com o conector.

**Notificações (push).** O sino no topo da lista de conversas liga e desliga. O aviso é um **toque sem texto**: aparece "Lacre · Você tem uma nova mensagem", sem nome nem conteúdo (o servidor nunca vê as mensagens, e o serviço de push do Google/Apple/Mozilla só vê que houve um toque). Com o Lacre aberto na tela, nenhum aviso aparece. Como funciona: o banco tem um gatilho (`notifica_mensagem`, via `pg_net`) que chama a função `notificar` (Edge Function em `supabase/functions/notificar/`, sem JWT, que faz a autenticação do pedido sozinha) para cada mensagem que quer aviso; a função confere que a mensagem existe, é do destinatário, tem menos de 2 min e ainda não foi avisada (marca `notificada` atômica, sem aviso em dobro), e manda um push VAPID (RFC 8292, ES256, `vapid.js`) **sem corpo** para os aparelhos da pessoa, com `Topic` (avisos acumulados viram um só). Inscrições expiradas (404/410) são apagadas. As chaves VAPID são criadas pela própria função na primeira chamada e ficam em `push_config` (tabela que ninguém logado lê); o navegador pega a chave pública em `GET /functions/v1/notificar`. O aparelho se registra por `registrar_push` (no máximo 5 por pessoa; o mesmo aparelho muda de dono se outra conta entrar; sair da conta tira o aparelho da lista). Mensagens invisíveis (`hello`, apagar) vão com `avisar=false` e não geram aviso (o servidor sabe só que são desse tipo). `reação` é igual a mensagem para o servidor, então também avisa. iPhone: só com o Lacre instalado na tela inicial (há `manifest.webmanifest` e ícones). Configuração por projeto: `insert into push_config values ('functions_url', 'https://<ref>.supabase.co/functions/v1')`. Se a chave VAPID for trocada, quem tem o sino ligado liga de novo (o app detecta e se reinscreve sozinho ao tocar no sino).

**Mensagens: menu e resposta por gesto.** Não há mais o botão "+" ao lado de cada mensagem. **Segurar** a mensagem (cerca de 0,4 s, com leve vibração) abre o menu: reagir (6 emojis), **Responder**, **Copiar** (texto) e **Apagar…**. No computador, o **botão direito** faz o mesmo; no teclado, Enter com a mensagem focada. **Arrastar a mensagem para a direita** (60 px) responde: um ícone de seta aparece e escurece ao passar do limite. Em telas de toque o texto das mensagens não é selecionável (use "Copiar").

**Abertura do site.** Quem já estava logado vai direto para as conversas: uma tela de abertura (marca "lacre") cobre tudo enquanto se confere a sessão, e a estrutura das conversas aparece antes de as chaves e os contatos carregarem (`#chat.preparando` só aceita toques quando tudo está pronto, `body[data-pronto]`). Com verificação em dois passos, nada abre antes do código. Em segundo plano, `getUser()` confere no servidor se a sessão ainda vale (ex.: senha trocada em outro aparelho): se não, cai no login. Ao abrir uma conversa, a lista só aparece pronta, já nas últimas mensagens.

**Arquivos guardados no aparelho.** Áudios, fotos, figurinhas e fundos baixados (ou enviados) ficam no IndexedDB, **cifrados do mesmo jeito que estão no servidor** (a chave de cada arquivo só existe dentro das mensagens, que já ficam cifradas aqui). Ouvir de novo não baixa nada, e áudio já guardado aparece com o player pronto. Limite de 300 MB no total, descartando os menos usados; cada arquivo até 50 MB (inclui vídeos). Apagar a mensagem apaga a cópia; "Sair e apagar chaves" apaga tudo. Áudio de 5 s ocupa ~25 KB.

**Gravar áudio:** segure o botão do microfone para gravar e **solte para enviar** (a barra vira "● 0:07 ‹ Deslize para cancelar"; o botão cresce e pulsa). **Arrastar para cima** (cadeado) **trava** a gravação: dá para soltar o dedo; aparecem lixeira, ondas de voz ao vivo (Web Audio) e o botão de enviar. **Arrastar para o lado** e soltar **cancela** (o botão não desliza para o lado, para não cobrir o texto; ele escurece e o texto vira "Solte para cancelar"). A barra de gravação aparece no instante do toque (sem espera); toque de menos de 0,25 s não grava e mostra uma dica, e áudio de menos de 1 s aparece como 0:01. Quem usa teclado ou leitor de tela aperta Enter/Espaço no botão: grava já travado, e o botão de enviar manda. Metadados saem do áudio antes do envio (como antes) e o limite é de 5 minutos. Gestos em `app.js` (`mic` + `pointer*`), estilos em `style.css` ("gravar áudio").

**Apagar mensagens:** no menu da mensagem (o "+" ao lado do balão) há "Apagar…". Em mensagem **própria** dá para **apagar para todos** (vai uma mensagem cifrada `{type:"delete", to:<id>}` para o amigo; nos dois aparelhos o texto guardado é trocado por "Mensagem apagada"; o arquivo cifrado de foto/vídeo/áudio sai do armazenamento; citações já na tela passam a mostrar "Mensagem apagada") ou **só para mim** (o aparelho guarda que a mensagem ficou escondida, sem aviso). Mensagem **recebida** só pode ser apagada para mim. O aviso "Mensagem apagada" também pode ser apagado, só para mim. Quem recebe o pedido confere no servidor que o autor da mensagem é quem mandou apagar (ninguém apaga mensagem alheia). Linhas no banco não são removidas (o app não tem permissão de DELETE em `messages`); o texto antigo não fica mais legível em nenhum aparelho, e com sigilo futuro o texto cifrado no servidor já é ilegível. Figurinhas não têm o arquivo removido (o mesmo arquivo é reaproveitado em outras mensagens). Versões antigas do site, ainda em cache, mostram o pedido como "não foi possível decifrar".

**Figurinhas:** botão de figurinhas ao lado do clipe. "Criar ou importar" aceita vários arquivos de uma vez (PNG, JPG, WebP, GIF). Figurinhas prontas (PNG/WebP com fundo transparente) e animadas entram direto; fotos inteiras abrem o editor de recorte, que segue o fluxo do notebook `recortador_figurinhas_sam2`: a pessoa toca no que quer recortar (pode tocar em vários pontos; tocar num ponto o remove; o botão de setas troca para o **ponto vermelho**, que diz ao modelo o que deve ficar de fora), o recorte aparece ao lado numa grade de transparência, e "Salvar figurinha" guarda um WebP 512×512 de até 100 KB. O recorte usa o **SAM 2.1 tiny** (Meta, Apache 2.0, ONNX int8) via ONNX Runtime Web, rodando em WebAssembly no próprio aparelho, em segundo plano (`sam2.js`; arquivos em `vendor/sam2/` ~62 MB e `vendor/ort/` ~15 MB, baixados só quando alguém abre o editor; a CSP ganhou `'wasm-unsafe-eval'` e `connect-src 'self'` só por isso). A foto é analisada uma vez (~10–15 s sem GPU) e cada toque seguinte leva ~0,2 s. O acabamento (`recorte.js`, valores em `recorte-config.js`): rampa de borda (BORDA_MIN/MAX), miolo opaco e buracos pequenos fechados, contorno branco, nota mínima da máscara. O resultado é redesenhado no canvas (sem metadados). GIF, WebP e PNG animados (até 1 MB e 1024 px) são guardados inteiros, sem recorte, só com os metadados removidos sem recodificar. A lista fica **só neste aparelho**, cifrada no IndexedDB (some em "Sair e apagar chaves"; não sincroniza entre aparelhos). Enviar uma figurinha é enviar mídia cifrada (`kind: "sticker"`); reenviar a mesma ao mesmo amigo reaproveita o arquivo já enviado. Quem recebe pode tocar em "Salvar figurinha". Lógica pura em `sticker.js` (limpeza de animadas) e `recorte.js` (acabamento), com testes em `tests/sticker.test.mjs` e `tests/recorte.test.mjs`.

**Trocar a senha de login:** "Segurança da conta → Trocar senha de login". Confere a senha atual num cliente descartável, exige 12+ caracteres (o servidor aceita 6, então a regra é do app), pede confirmação e, ao concluir, encerra as sessões dos outros aparelhos. Com 2FA ativo o servidor só aceita a troca em sessão que já passou pelo código (aal2). A senha de login não protege as mensagens: trocá-la não afeta a chave nem a frase-senha.

**Login:** o Supabase Auth só limita depois de centenas de tentativas por minuto de um mesmo IP (medido: o primeiro bloqueio veio após ~340 tentativas em ~8 s), e senhas erradas não bloqueiam a conta. Por isso: senha nova com 12+ caracteres, e no painel (Authentication) reduzir os limites de tentativas e exigir senha mínima de 12. A mensagem protegida não depende da senha de login: sem a chave do aparelho (ou a frase-senha) o atacante não lê nada.

## Verificação em dois passos (TOTP)
Opcional por conta: botão do escudo no cabeçalho da lista → "Ativar" → escanear o QR num app autenticador (Google Authenticator, Authy, Microsoft Authenticator…) → digitar o código de 6 dígitos.
- Depois de ativada, o login pede o código **antes** de qualquer coisa (inclusive antes da frase-senha num aparelho novo). Recarregar a página não pede de novo; entrar numa sessão nova, sim.
- **Vale no banco, não só no site:** as tabelas, o storage e o realtime têm políticas *restritivas* (`public.mfa_ok()`): uma sessão só com senha não lê perfil, mensagens nem backup da chave, não envia, não busca amigos nem lista arquivos. Desativar também exige o 2º passo.
- **Perdeu o celular?** Cadastre o mesmo QR/chave em dois aparelhos assim que ativar. Se perder todos, o administrador remove o fator (SQL em `supabase/monitoramento.sql`, item 9) depois de confirmar que é a pessoa.
- **Chutar o código:** o Supabase limita as verificações por IP (medido: bloqueio após ~30 tentativas em segundos). Em *Authentication → Rate Limits*, deixe **"token verifications"** em 5 por 5 minutos: é esse limite que protege o código de 6 dígitos.

## Responder a mensagens
No menu de cada mensagem (botão **+**) há **Responder**: texto, foto, vídeo ou áudio. Aparece a barra "Respondendo a…" acima do campo (cancela no **×** ou com **Esc**), e a resposta chega com a citação no topo do balão; tocar nela rola até a original e a destaca.
- A citação (id da original, autor e um resumo de até 80 caracteres) viaja **dentro da mensagem cifrada**: o servidor não vê qual mensagem foi respondida, e nenhuma mudança no banco foi necessária. Fica no histórico local, então volta ao recarregar.
- **Anti-forja:** o que chega de outra pessoa é validado (`reply.js`, com testes) e, quando a mensagem original está na tela, o texto e o autor mostrados vêm **dela**, não do resumo recebido. Assim, um amigo mal-intencionado não consegue fazer parecer que você escreveu algo que não escreveu. Se a original não está carregada (mensagens muito antigas), mostra o resumo recebido em itálico e avisa ao tocar.
- Reações e mensagens de controle não são citáveis; responder a uma resposta cita só a mensagem anterior (sem aninhar).

## Guarda de entrada (`guarda.js`)
O `index.html` não carrega o app direto: carrega o `guarda.js`, que decide primeiro e só então faz `import("./app.js")`.
- **Navegadores embutidos** (Instagram, Facebook, Messenger, TikTok, Snapchat, WebView genérica do Android...) são **bloqueados**: o aplicativo que hospeda a tela consegue executar código dentro da página e ler o que aparece nela (mensagens já decifradas) e o que ela guarda. A tela de bloqueio ensina a abrir no navegador de verdade (no Android há botão que tenta abrir direto no Chrome). Quando bloqueia, o app **nem é carregado**: nenhuma chave é aberta e nenhum banco local é criado.
- **Dentro de moldura (iframe) de outro site:** também bloqueado (clique disfarçado). O GitHub Pages não deixa mandar o cabeçalho `frame-ancestors`, então esta é a defesa possível; com Cloudflare Pages dá para usar cabeçalhos de verdade.
- Limite honesto: o Safari View Controller do iPhone não se identifica, então não dá para detectá-lo.

## Frase-senha do backup
Mínimo de **16 caracteres** (e pelo menos 8 diferentes) para frases novas; "Segurança da conta → Trocar frase-senha" permite fortalecer uma frase antiga (pede confirmação digitada duas vezes). É o ponto que decide o dano se alguém descobrir a senha de login de uma conta sem 2FA: o backup cifrado pode ser atacado fora do site, sem limite de tentativas. Cinco palavras sorteadas ("rio-lua-pedra-nuvem-cafe") aguentam; "eduardo2026!" não.

## Foto de perfil
Toque no círculo ao lado do seu @ (topo da lista) → escolher foto → arraste e use o zoom → Salvar (ou Remover foto). O navegador recorta em quadrado 256×256, descarta os metadados (local, câmera) e guarda em WebP/JPEG de até 100 KB. A foto aparece na lista de conversas e no topo da conversa de quem já trocou mensagem com você.
- Bucket privado `avatars` (`supabase/avatar.sql`): só o dono envia/apaga (no máximo 5 arquivos, o app apaga a antiga), só o dono e quem já conversou com ele leem; a coluna `profiles.avatar` só aceita um caminho da própria pasta. A política "exige dois passos" vale aqui também.
- **Diferente das mensagens, a foto NÃO é cifrada de ponta a ponta**: o servidor consegue ver. Se isso incomodar, dá para cifrar a foto e mandar a chave pela conversa.
- Testes: `tests/avatar.test.mjs` (recorte e nomes) e `tests/e2e/avatar.test.mjs` (envio, quem vê, estranhos, formatos e limites).

## Histórico para outro aparelho (exportar / importar)
Por causa do sigilo futuro, um aparelho novo não consegue ler as mensagens antigas (as chaves delas foram apagadas). Em **Segurança da conta → Exportar histórico** o aparelho antigo gera um arquivo `.lacre`; no aparelho novo, **Importar histórico** traz tudo de volta.
- O arquivo é cifrado no navegador com AES-256-GCM; a chave vem de uma senha própria dele (PBKDF2-SHA256, 1.000.000 de voltas). O app gera uma senha de 20 símbolos sorteados (~99 bits) ou aceita uma sua (16+ caracteres). Não vai para o servidor.
- Só abre na MESMA conta (o id da conta é dado autenticado). Senha errada, conta errada e arquivo alterado dão o mesmo erro.
- Importar só ACRESCENTA: o que o aparelho já tem nunca é sobrescrito, e importar duas vezes não duplica. Apagadas para todos/para mim continuam apagadas.
- Inclui o texto e as chaves dos arquivos de mídia (que seguem no servidor, cifrados). Figurinhas salvas e o cache de arquivos não entram.
- O arquivo é uma cópia legível do histórico para quem tiver arquivo + senha: guarde só onde você controla e apague depois de importar.
- Testes: `tests/historico.test.mjs` e `tests/e2e/historico.test.mjs` (aparelho novo não lê → exporta → importa → lê).

## Vídeos comprimidos no envio
Ao anexar um vídeo MP4/MOV, o app comprime no próprio aparelho (WebCodecs): **720p (lado menor), ~2 Mbps, até 30 fps, H.264**, mantendo o **áudio AAC original sem recomprimir**. Mostra "Comprimindo vídeo… X%" (dá para cancelar no ×) e depois "NN MB · comprimido de MM MB · metadados removidos". Entrada de até 300 MB; o resultado precisa ficar em até 45 MB.
- **Sem bibliotecas de terceiros:** `video.js` lê o MP4 de origem e monta o novo MP4 do zero (só as caixas mínimas), então o arquivo não herda nenhum metadado (local, aparelho, datas). O código roda no mesmo contexto do app: por isso não há dependência externa para auditar.
- **Quando não comprime (envia como antes):** navegador sem WebCodecs; vídeo já leve (≤ 720p e ≤ 3 Mbps); MP4 fragmentado; áudio que não é AAC; vídeo de 10 bits/HDR; HEVC que o navegador não decodifica; qualquer erro ou resultado que não fique ≥ 10% menor. Nesses casos vale o limite de 45 MB do original.
- **Cache:** os vídeos também ficam guardados no aparelho (limite por arquivo: 50 MB; total do cache: 300 MB, com descarte dos menos usados).
- Testes: `tests/video.browser.test.mjs` (ffprobe/ffmpeg conferem codec, tamanho, duração, rotação, áudio idêntico, ausência de metadados e decodificação sem erros) e `tests/e2e/video.test.mjs`.

## Aparelhos conectados
Menu da foto → Segurança da conta → **Aparelhos conectados**: lista os acessos à conta (mais novo primeiro): navegador e sistema ("Chrome no Android"), local aproximado, data/hora de entrada e do último acesso, "Este aparelho" para o atual e "Sessão ativa" / "Saiu" para os outros. Atalho "Não reconheço um aparelho: trocar a senha" (trocar a senha desconecta todos os outros aparelhos).
- A Edge Function `aparelho` (exige login) registra a sessão atual: navegador/sistema/tipo (rótulos do User-Agent; o texto bruto NÃO é guardado), data e local. **O IP não é guardado.** O local vem de uma consulta server-a-server ao serviço público **ipwho.is** só com o IP (sem nome, conta ou mensagens), uma vez por sessão por dia. Se o serviço falhar, aparece "Local indisponível". Para desligar a região, basta remover a função `local()` de `supabase/functions/aparelho/index.ts`.
- Tabela `public.aparelhos` (RLS ligada, sem acesso direto; só a função `meus_aparelhos()` lê, e só as linhas da própria pessoa, exigindo o 2º passo). Guarda no máximo os 30 acessos mais recentes de cada pessoa.
- **"Sair" agora só desconecta o aparelho atual** (antes desconectava a conta em todos os aparelhos).
- Testes: `tests/aparelho.test.mjs` e `tests/e2e/aparelhos.test.mjs`.

## Aviso de aparelho novo
Quando OUTRO aparelho entra na conta, os aparelhos que já estavam conectados mostram, ao abrir o Lacre (ou ao voltar para a aba, ou a cada minuto com a aba aberta), uma **folha** com o aparelho, o local aproximado e a data/hora do primeiro acesso, e duas saídas: **"Sou eu, conheço este aparelho"** (reconhece e some) e **"Não fui eu: trocar a senha"** (marca como não reconhecido e abre a troca de senha, que desconecta os outros aparelhos). Fechar a folha sem decidir deixa um **ponto rosa** na foto (e uma linha em Segurança da conta) até a pessoa conferir; em Aparelhos conectados o aparelho aparece com "Novo" e os botões "Reconheço / Não reconheço". Um "não reconhecido" que ainda está conectado mantém o ponto até sair.
- Quem acabou de entrar não é avisado de si mesmo. O PRIMEIRO aparelho da conta, e quem volta com o mesmo navegador + sistema + tipo + estado de um aparelho já reconhecido, entram como reconhecidos (sem aviso). Se o local de um dos dois não deu para saber, isso não conta como diferença.
- A decisão é guardada em `public.aparelhos.decisao` (`reconhecido` / `recusado`); só a função `decidir_aparelho()` altera, só para sessões da própria pessoa e nunca para a sessão que está decidindo.
- Limite: o aviso só aparece quando o Lacre está aberto (não manda e-mail). Testes: `tests/e2e/aparelhos.test.mjs`.

### Código do aparelho (como o Lacre sabe "quem é quem")
Cada navegador cria um **código aleatório** (`lacre:disp` no armazenamento do site) na primeira vez. O servidor guarda só `SHA-256(id_da_conta:código)`, nunca o código. Quem volta com um código **já reconhecido** (mesmo em outro navegador ou depois de sair e entrar) não gera aviso; um código novo, mesmo no mesmo tipo de navegador e sistema, gera. Limpar os dados do site ou usar aba anônima cria um aparelho novo (pede conferência uma vez). Sessões antigas ganham o código na próxima vez que abrem o app.
- O **IP não identifica aparelho** (vários aparelhos na mesma rede dividem o IP; o mesmo aparelho troca de IP). Ele só vira **pista de risco** pelo local aproximado: o aviso destaca "Local muito diferente do seu uso normal" (outro país) ou "Em outro estado" em relação aos aparelhos já reconhecidos (`aparelhos.js`).

## Vários aparelhos na mesma conta: etapa 1 (permissão entre aparelhos)
Hoje todos os aparelhos de uma conta compartilham a chave de identidade (restaurada pela frase-senha), mas quem envia cifra UMA cópia, então só um aparelho lê. O plano é cada aparelho receber a sua cópia; esta primeira etapa só prepara o terreno e **não muda o envio nem o recebimento de mensagens**.
- **Identificador do aparelho:** cada navegador cria um código aleatório (32 caracteres hexadecimais) por conta, guardado cifrado no armazenamento local (IndexedDB, junto das sessões). Sobrevive a sair e entrar de novo; some em "Sair e apagar chaves" (que também tira o aparelho da lista da conta). É segredo do aparelho: o servidor o guarda, mas nenhuma função o devolve; a tela usa um código à parte (`ref`).
- **Regras (no banco, funções `SECURITY DEFINER`; tabelas `dispositivos` e `dispositivo_sessoes` sem acesso direto):** o primeiro aparelho da conta entra **permitido**; os seguintes entram **pendentes** e só passam a valer quando um aparelho **já permitido** da mesma conta permitir (o servidor sabe de qual aparelho vem a chamada pela sessão de login). Recusar apaga o registro e as chaves de recepção dele **e encerra as sessões de login dele** (o aparelho é desconectado: percebe ao conferir, volta para o login e, se entrar de novo, é um pedido novo, pendente); remover OUTRO aparelho (permitido ou pendente) faz o mesmo; um aparelho pode remover a si mesmo (e sai); um pendente não permite, recusa nem remove os outros. No máximo **5 aparelhos** por conta (pendentes contam); registrar de novo o mesmo código é idempotente. Se o último aparelho permitido sai, o pendente que abrir o Lacre depois vira o primeiro (senão ninguém poderia permitir).
- **Chaves de recepção marcadas:** `prekeys.aparelho` guarda de qual aparelho é cada chave (nula nas antigas). O banco só aceita a marca do aparelho da própria sessão, e a coluna não é legível por quem está logado (um aparelho pendente não descobre o código dos outros). O app troca a chave de recepção uma vez para ela passar a levar a marca. `get_prekey` continua igual: ainda não filtra por aparelho.
- **Tela "Aparelhos conectados":** nova seção "Aparelhos da conta" (este aparelho, selo "Aguardando permissão", Permitir / Recusar só num aparelho permitido, Remover) acima de "Acessos recentes" (o histórico de sessões, como antes). Num aparelho pendente há um aviso de que falta um aparelho já conectado permitir; num permitido, uma faixa no topo da lista de conversas avisa quando há pedido (ao abrir, ao voltar para a aba e a cada minuto). (A etapa 2, abaixo, passou a usar o estado: aparelho pendente não participa.)
- **O que ainda não mudou:** a mensagem continua cifrada para um aparelho só (o que falou por último), o aviso de "aparelho novo" (sessões) é independente deste e a busca de chaves não filtra por aparelho. Próximas etapas: enviar uma cópia por aparelho permitido e deixar de usar chaves de aparelhos pendentes.
- Testes: `tests/dispositivos.test.mjs` (funções puras), `tests/e2e/dispositivos.test.mjs` (dois navegadores na mesma conta: permitir, recusar, remover, limite, idempotência), `tests/e2e/security.test.mjs` (ataques no banco) e `tests/static.test.mjs`.

## Vários aparelhos na mesma conta: etapa 2 (uma cópia cifrada por aparelho)
Nas conversas **a dois**, cada mensagem agora vai cifrada separadamente para **cada aparelho permitido** de quem recebe e para **cada outro aparelho permitido** de quem envia. Resultado: todos os aparelhos permitidos leem as mensagens novas e veem o que os outros aparelhos da mesma conta enviaram, no lugar certo e como "minha" (some o aviso "Enviada por você de outro navegador" para mensagens novas). **Grupos continuam como antes** (etapa 3). Mensagens antigas não migram: um aparelho só lê o que chega depois de ser permitido.

**Protocolo (sem criptografia nova).** Mesmas primitivas de `ratchet.js` (3DH + Double Ratchet): uma **sessão por (pessoa, aparelho)**. No `store.js` a sessão fica sob `"<id da pessoa>#<ref do aparelho>"` (cada lado chama a sessão pelo ref do OUTRO aparelho); o histórico continua sob o id da pessoa. Sessões e mensagens do formato antigo (sem ref) seguem valendo.
- **Linha no servidor** (`messages`): `para_aparelho` = `ref` (código público, nunca o identificador secreto) do aparelho de destino; `de_aparelho` = `ref` do aparelho que enviou, **preenchido pelo servidor** (o cliente nem tem permissão de gravar a coluna). Nulo = formato antigo.
- **Dentro do conteúdo cifrado:** texto e mídia levam `mid` (32 hex), o mesmo em todas as cópias (cada aparelho recebe uma linha diferente, então o id da linha deixa de identificar a mensagem). Responder (`re.mid`), reagir (`to`) e apagar para todos (`to`) apontam para o `mid`; mensagens antigas (por id) continuam usando o caminho antigo. A **cópia para meus outros aparelhos** é uma linha de mim para mim (`recipient_id = eu`, `para_aparelho` = outro aparelho meu) cujo conteúdo leva `para: <id da conversa>`; o aparelho que recebe a guarda no histórico daquela conversa como mensagem minha. Tudo que chega é validado (`copiaPropriaValida`): só vale linha de mim para mim, de OUTRO aparelho meu, com `para` válido. Vale também para reações e apagar; `hello` (refazer sessão) só vai para quem recebe.
- **Quem envia** busca `get_prekeys_aparelhos(pessoa)` (aparelhos aprovados com a chave de recepção mais recente de cada um), guarda a lista por 60 s e a refaz quando o servidor recusa (42501: alguém foi removido/permitido), tentando UMA vez de novo. No máximo 5 + 4 = 9 linhas por mensagem, num único `insert`. **Sem aparelho aprovado** do destinatário (conta que ainda não abriu o site novo), ou sem este aparelho registrado, envia no formato antigo (uma cópia, `para_aparelho` nulo). Uma pessoa recém-permitida só passa a receber quando as listas dos contatos se atualizam (até ~60 s) e sua chave de recepção estiver publicada.
- **Aparelho falso:** se um servidor malicioso enfiasse um aparelho na lista, ele não abre a sessão: o acordo de chaves (3DH) usa a chave de IDENTIDADE da conta, que só os aparelhos com a frase-senha têm. O aparelho falso recebe uma linha ilegível; o envio para os outros aparelhos segue funcionando (teste em `multiaparelho.test.mjs`).

**Quem enxerga o quê, no servidor (RLS e gatilhos, não só no app).**
- Linha com `para_aparelho`: só o aparelho de destino lê (política usa `dispositivo_atual()` pela sessão do JWT), além de quem enviou (para o status): a conta que enviou lê as linhas endereçadas a outros; a **cópia para mim mesmo** só o aparelho de destino lê (e o que a criou, porque o `insert ... returning` precisa). O Realtime respeita a política (teste: o aparelho A não recebe a cópia do B, nem o pendente, nem outra conta).
- O gatilho de inserção recusa (42501) `para_aparelho` que não seja aparelho **aprovado** de `recipient_id` (pendente, removido, de outra conta, inexistente); cópia para mim só para OUTRO aparelho meu aprovado; cópia por aparelho não vale em grupo.
- **Aparelho pendente não participa:** não lê (nem o formato antigo), não envia, e não aparece em `get_prekeys_aparelhos`; `get_prekey` (antiga, para o formato antigo e grupos) também não devolve chave de pendente. Sessão de login **sem aparelho registrado** (site antigo em cache) continua lendo só o formato antigo, como antes. No app o pendente vê uma tela cheia **"Aguardando permissão"** (sair; "Não tenho mais acesso aos outros aparelhos") e, ao ser permitido, entra sozinho.
- **Lida:** ler num aparelho chama `marcar_lidas` (servidor), que marca também as cópias dos meus outros aparelhos (a bolinha de não lida some neles, por tempo real ou ao abrir). Para quem enviou, "vista" = algum aparelho do destinatário leu (cópias próprias não contam).
- **Push:** um aviso por mensagem por pessoa (só a linha de menor id da leva avisa) e nenhum para cópia própria; regra de grupos (`grupo_id is null or citado`) igual.
- **Limites:** uma mensagem a dois vira até 9 linhas, então o limite por minuto (300 linhas) passa a valer ~33 mensagens/min a dois com 5+4 aparelhos (não mexi nos limites). Estatísticas e Selos contam só linhas de grupo (`grupo_id`), então não mudam.

**Recuperação ("perdi o único aparelho"): 24 horas, tudo no servidor.** O aparelho pendente pede (`pedir_recuperacao`); o banco guarda a hora (`dispositivos.recuperacao_pedida_em`; um pedido por vez por aparelho; cancelar é possível). Os aparelhos permitidos veem um aviso claro (faixa no topo e em Aparelhos conectados, com a hora em que vale) e podem **Recusar** (já desconecta o pendente). Passadas 24 h pelo relógio do banco sem recusa, o pendente chama `concluir_recuperacao`: todos os OUTROS aparelhos (e todas as outras sessões de login da conta) são removidos e desconectados e ele vira o único permitido. **Não há atalho:** a regra antiga "se não sobrou nenhum aprovado, o pendente vira aprovado ao reabrir" foi removida (senão "Sair e apagar chaves" no único aparelho aprovado entregaria a conta a um pendente invasor); só o primeiro aparelho de uma conta SEM nenhum permitido entra permitido. O prazo é de `recuperacao_prazo()` (24 h; um valor interno em `push_config` só para o projeto de teste encurtar, que ninguém logado lê ou escreve). Não há aviso fora do app (e-mail/push) para o pedido: quem abre o Lacre num aparelho permitido vê a faixa.

**Limitações conhecidas.** (1) Grupos: com vários aparelhos, a mensagem de grupo (formato antigo, uma cópia por pessoa) só abre no aparelho que tem a chave de recepção usada; nos outros a linha some em silêncio (sem balão de erro). Etapa 3. (2) Até ~60 s depois de um aparelho ser permitido, quem envia ainda usa a lista antiga. (3) O pendente de um site antigo (etapa 1) deixa de ler e enviar assim que o banco é atualizado.
- Testes: `tests/dispositivos.test.mjs` e `tests/grupo.test.mjs` (funções puras), `tests/e2e/aparelhos2-seguranca.test.mjs` (regras do banco), `tests/e2e/multiaparelho-tempo-real.test.mjs` (o tempo real respeita a política), `tests/e2e/multiaparelho.test.mjs` (dois navegadores por pessoa, ponta a ponta). No projeto de teste, `insert into push_config values ('recuperacao_prazo', '8 seconds')` deixa a recuperação testável de ponta a ponta (sem isso, a parte "passado o prazo" é pulada).

## Grupos
Botão **Chamar → Criar um grupo**: dê um nome e marque as pessoas (só aparece quem já conversa com você). O grupo entra na lista de conversas (quadrado de cantos redondos, com a inicial do nome; pessoas são círculos). No topo da conversa, o botão de pessoas abre **Dados do grupo**: participantes, quem é admin, mudar o nome, adicionar, remover e sair.

**Como a mensagem viaja.** Não existe uma "chave do grupo" que abra as mensagens. Cada mensagem é cifrada **separadamente para cada participante**, pela mesma sessão com sigilo futuro (Double Ratchet) das conversas a dois, e gravada num pedido só (uma linha por pessoa em `messages`, marcada com `grupo_id`): ou chega para todos, ou para ninguém. Quem sai ou é removido simplesmente deixa de receber cópias; quem entra só lê o que for enviado depois. Fotos, vídeos, áudios e figurinhas são cifrados e enviados **uma vez** (`{remetente}/{grupo}/{arquivo}`); a chave do arquivo vai dentro de cada cópia cifrada da mensagem.

**O que o servidor sabe e o que não sabe.** Sabe quem participa de cada grupo (precisa, para recusar mensagem de quem não é do grupo e liberar os arquivos só para participantes). Não lê as mensagens nem o **nome** do grupo: o nome é cifrado (AES-GCM) com uma chave aleatória do grupo, que chega a cada participante embrulhada na cifra a dois de quem o adicionou. O nome fica preso ao id do grupo (dado autenticado), então não dá para trocar nomes entre grupos.

**Cargos.** Três níveis: **admin** (quem cria o grupo): faz tudo; **sub-admin**: só **remove membros comuns** (não remove o admin nem outro sub-admin) e não dá cargo a ninguém; **membro**: conversa e pode sair. Só o admin dá ou tira o cargo de sub-admin (botão de escudo ao lado do nome, em "Dados do grupo"), muda o nome, adiciona pessoas e troca a foto. Se o admin sai, assume o sub-admin mais antigo (ou, sem sub-admin, o membro mais antigo). Entrada, saída e mudança de cargo viram avisos na conversa.

**Foto do grupo.** Só o admin troca (botão da câmera em "Dados do grupo"; recorte quadrado no centro, 256 px). A foto é **cifrada com a chave do grupo** (a mesma que cifra o nome) antes de ir para o servidor, no bucket `media` (`{admin}/{grupo}/{arquivo}`), e a tabela `grupos` guarda só o caminho e o IV (`grupo_foto()` recusa caminho fora da pasta do grupo). Diferente da foto de perfil, o servidor não consegue ver a imagem.

**Citar alguém (@).** Ao digitar `@` aparece uma lista com os participantes (sem você), que vai filtrando conforme se digita; toque, Enter ou Tab escolhe. O nome citado fica em destaque para todos, e mais forte (com uma barra rosa na mensagem) para quem foi citado. Só valem nomes de quem está no grupo; e-mails (`a@b.com`) e nomes de fora ficam como texto. **Aviso:** só a linha de quem foi citado leva a marca `citado` (`messages.citado`), e só ela dispara o push, se a pessoa estiver fora do site (com o Lacre aberto na tela nada aparece). **Mudança:** mensagem comum de grupo **não avisa mais** por push (antes avisava todo mundo); conversa a dois continua avisando. O servidor não vê o texto, mas fica sabendo **quem foi citado** (a marca é uma coluna): é o preço de o aviso funcionar com o site fechado. O texto do aviso é o mesmo de sempre ("Você tem uma nova mensagem").

**Regras (todas conferidas no banco, por funções `SECURITY DEFINER`; as tabelas `grupos` e `grupo_membros` não são legíveis nem graváveis direto):**
- quem cria é admin; só admin adiciona, remove e muda o nome; qualquer um sai;
- só entra num grupo quem **já conversou** com quem está adicionando, nos dois sentidos (um desconhecido não coloca você num grupo só por ter mandado uma mensagem);
- se o admin sai, quem está há mais tempo assume; quando a última pessoa sai, o grupo e as mensagens dele são apagados do servidor;
- mensagem com `grupo_id` só entra se quem envia **e** quem recebe estão no grupo.

**Proteções do lado do aparelho.**
- A linha do servidor diz de qual grupo a mensagem é, e o conteúdo cifrado diz a mesma coisa; se não baterem, a mensagem é recusada (`conteudoBate` em `grupo.js`). O servidor não consegue jogar uma mensagem particular dentro de um grupo, nem levar uma mensagem de um grupo para outro.
- Cada aparelho anota quem estava em cada grupo. Quando a lista muda, aparece um aviso no meio da conversa ("@fulano entrou no grupo", "saiu", "o grupo agora se chama…"): ninguém entra num grupo sem os outros verem.
- Responder, reagir e apagar apontam para um identificador da mensagem que viaja cifrado (cada pessoa recebe a mensagem numa linha diferente do servidor). "Apagar para todos" só vale se vier de quem escreveu.
- A verificação por código de segurança continua sendo feita pessoa a pessoa, na conversa a dois (em Dados do grupo, o balão ao lado do nome abre essa conversa).

**Sincronização.** Ao abrir o Lacre (e ao voltar para a aba), tudo o que chegou com ele fechado é decifrado em ordem, numa fila única. Sem isso, uma mensagem de grupo só seria lida quando a conversa a dois com quem a mandou fosse aberta. De quebra, as conversas com mensagem nova ganham a bolinha de não lida logo ao abrir, e a lista fica ordenada pela atividade mais recente.

**Limites e custos.** Até 20 pessoas por grupo. Uma mensagem num grupo de N pessoas ocupa N−1 linhas no banco (é o preço de não ter uma chave compartilhada); por isso o limite de envio é contado em linhas. Em grupo não há "vista". Nos grupos (até a etapa 3), o que você envia de um aparelho não é legível em outro aparelho seu (aparece o aviso "Enviada por você de outro navegador ou aparelho"); nas conversas a dois isso já não acontece (etapa 2).

## Botão "voltar" do celular
Cada tela que abre por cima (conversa, páginas de configuração, janelas de pergunta e aviso, foto ampliada, menu da conta, menu da mensagem, bandeja do "+") ganha uma entrada no histórico do navegador (`history.pushState`): o "voltar" do celular fecha a tela de cima, uma por vez, em vez de sair do site. Se a tela é fechada pelo próprio app (setinha, Cancelar), a entrada é desfeita junto, então nunca sobra um "voltar" à toa. Da lista de conversas, "voltar" sai do site, como em qualquer página. Depois de recarregar a página, o navegador ainda guarda as entradas da página antiga: pode ser preciso um "voltar" a mais para sair. Teste: `tests/e2e/voltar.test.mjs`.

## Vídeos curtos nas conversas (YouTube Shorts, Instagram Reels, TikTok)
Um link desses três (só nos endereços exatos: `youtube.com/shorts/ID`, `instagram.com/reel/CÓDIGO`, `tiktok.com/@perfil/video/ID`, com ou sem `www`/`m.` e com o `/pt-BR/` do TikTok) vira um **cartão** no balão, com a etiqueta da rede, o botão de play e a cor da rede (a capa real exigiria contatar a rede, então não há). **Tocar** abre uma **tela cheia** com o vídeo, o botão "Abrir no YouTube/Instagram/TikTok" e a setinha (o "voltar" do celular também fecha). Links parecidos (`youtube.com.evil.com`, `site@youtube.com`, `http://`, `/watch?v=`, `youtu.be`, `vm.tiktok.com`, Instagram `/p/`) **não** viram cartão: o endereço é lido com `URL()`, o servidor é conferido por inteiro e o código do vídeo precisa ter o formato certo (`videolink.js`, com testes). O player é aberto por um endereço **limpo, montado pelo Lacre** (o `?si=`/`?igsh=` do link original é descartado).

**Privacidade.** Nenhuma rede é contatada antes do toque. Ao tocar, a rede vê o **IP, o aparelho e qual vídeo foi aberto** (e por quanto tempo), nunca a conversa nem quem mandou. Na primeira vez de cada rede, um aviso explica isso, com "Assistir e não perguntar de novo" (guardado só neste aparelho, por rede). A moldura roda isolada: `credentialless` (sem os cookies de login; Chrome/Edge), `referrerpolicy` sem referência (exceto o YouTube, que recusa o player sem saber o site: ele vê o endereço do Lacre, não quem é você), `sandbox` sem navegação da página, downloads, formulários nem janelas modais, e `allow` só com autoplay/tela cheia/picture-in-picture (nada de câmera, microfone ou localização). O YouTube usa `youtube-nocookie.com`. A política de segurança (`index.html`) ganhou `frame-src` só com esses três endereços, sem curinga; o resto continua `default-src 'none'`.

**Limites.** Não dá para esconder o IP nem o aparelho da rede: ela precisa deles para entregar o vídeo. Sem login (cookies bloqueados), muitos Reels do Instagram pedem entrar e não tocam: o botão "Abrir no Instagram" cobre esse caso. Os testes usam um player de mentira (não contatam as redes de verdade); a reprodução real depende de cada rede aceitar o embed.

## Lista de conversas: mensagens novas, horário e quem está online
- **Mensagens novas:** cada conversa (pessoa ou grupo) mostra uma bolinha rosa com quantas mensagens novas chegaram (99+ a partir de 100). A contagem é guardada neste aparelho junto com o id de cada mensagem, então continua depois de recarregar e **nunca conta a mesma mensagem duas vezes** (chegar pelo tempo real e depois pela sincronização ao abrir). Abrir a conversa zera. Só entram mensagens de verdade: reação, "apagar" e avisos automáticos não contam. Não entram as mensagens que você mesmo enviou.
- **Horário da última mensagem:** hoje, a **hora** (`14:05`); de 1 a 6 dias atrás, o **dia da semana** (`Terça`); a partir de 7 dias, a **data completa** (`04/11/2026`). Passados 7 dias o nome do dia se repetiria e confundiria, por isso a data. Ao parar o mouse (ou segurar), aparece a data por extenso. O dia é contado pelo relógio do aparelho. Regra em `lista.js`, com testes. A hora vem do servidor só até a conversa ser aberta aqui: a partir daí é a da última mensagem que apareceu na tela (o servidor não consegue distinguir uma reação de uma mensagem, porque o conteúdo é cifrado).
- **Grupos:** a linha mostra `grupo · 5 pessoas · 3 online`, contando quem do grupo está online agora (sem você), pelo mesmo canal de presença das conversas a dois.
- **Teclado:** ao abrir uma conversa, o teclado **não sobe sozinho** no celular (aparelhos de toque); só aparece quando a pessoa toca no campo de mensagem. No computador, com mouse, o foco continua indo direto para o campo. Depois de enviar, o teclado só fica aberto se já estava aberto (enviar áudio ou figurinha não o abre).

## Como publicar (CI em duas etapas)
A suíte completa (unitários + ~320 testes de navegador, uns 5 minutos) roda **uma vez só**, no GitHub, **antes** de o código chegar na `main` (que publica o site):
1. `scripts/publicar.sh teste`: envia o commit para a branch `ci/teste` e espera o CI terminar. Antes disso, só se roda localmente os testes do que mudou (1 a 3 minutos), como verificação rápida.
2. Se houve mudança de banco: o CI local já aplica o `supabase/schema.sql` (atualize esse arquivo junto); aplicar também no projeto de teste hospedado antes da etapa 1 (os 2 arquivos das Edge Functions usam ele) e no banco real **depois** de o CI passar (banco primeiro, depois o código).
3. `scripts/publicar.sh main`: leva o **mesmo commit** (mesmo hash) para a `main`. O script recusa se aquele hash não tem um CI completo e bem-sucedido em outra branch. Na `main`, o CI só confere isso e **pula os testes** (o hash identifica o conteúdo exato, então não há o que repetir). Um envio direto à `main` sem ter passado antes roda tudo normalmente.
O CI continua só com permissão de leitura de conteúdo (mais `actions: read`, para conferir o hash). Sem mudança nos testes nem nas regras de segurança: só muda **onde e quando** eles rodam. O arquivo do ffmpeg deixou de rodar `apt-get update` antes de instalar quando não precisa (uns 15 s a menos por trabalho).

## Vários aparelhos na mesma conta: etapa 3 (grupos)
A mensagem de grupo também vai com uma cópia cifrada para CADA aparelho aprovado de cada participante e para os outros aparelhos de quem envia (`enviarVarios` em `app.js`; as linhas são montadas por `trabalhosDeEnvio`, em `dispositivos.js`). Quem ainda não usa aparelhos recebe uma cópia só, no formato antigo, na mesma leva.
- **Um pedido só** (ou chega para todos, ou para ninguém): por isso as estatísticas e os Selos continuam contando UMA mensagem por envio (`count(distinct created_at)`; há teste).
- **Cópia para os meus outros aparelhos:** linha de mim para mim com o grupo na linha E dentro do conteúdo cifrado (os dois têm de bater: `copiaGrupoValida`); o aparelho que a recebe guarda no histórico do grupo como mensagem minha. Reagir e apagar para todos seguem o mesmo caminho.
- **Ao abrir o grupo**, as minhas linhas viram uma mensagem (`lotesGrupo`); a que OUTRO aparelho meu enviou não aparece por aí (seria o balão "Enviada por você de outro aparelho"): aparece pela cópia.
- **No banco:** saiu a restrição que proibia `para_aparelho` em grupo; a policy de envio aceita linha para mim mesmo num grupo só como cópia para OUTRO aparelho meu aprovado (o gatilho `confere_aparelho_mensagem` confere) e só se eu participo do grupo; um pedido leva até 100 linhas; o limite por pessoa passou a contar mensagens (300/min, 5000/h), com teto de linhas à parte (3000/min, 30000/h).
- **O que ainda fica do formato antigo:** sessões de login sem aparelho registrado e chaves de recepção sem marca continuam aceitas, para quem ainda não abriu o site novo. Enquanto isso existir, a aprovação de aparelho não vale contra quem fala direto com o banco usando a senha, o 2º passo e a frase-senha da conta. Fecha quando todos os aparelhos em uso estiverem registrados.
- Mensagens antigas do grupo não passam para um aparelho novo (como na conversa a dois).

## Abrir uma conversa na hora
Ao abrir uma conversa (a dois ou em grupo), as últimas 200 mensagens que o aparelho **já guarda** (histórico local, em `store.js: recentesDoHistorico`, leitura pelo fim do índice, sem carregar tudo) são pintadas **na hora** (`pintarDoAparelho` em `app.js`), em vez de esperar as consultas ao servidor e a decifragem (antes 1 a 1,5 s com a lista escondida). A lista é montada escondida e só aparece pronta, já nas últimas mensagens; as **reações** guardadas (chips) e os **balões de aviso** que o aparelho já mostrou ("não foi possível decifrar", "enviada de outro aparelho", lembrados em `ph:<conversa>`) vêm junto. Sem histórico local (aparelho novo), tudo funciona como antes.
**Áudios em sequência:** ao tocar num áudio, os áudios **seguidos logo abaixo** (de quem for, seus ou do contato) tocam sozinhos, um depois do outro, até aparecer algo que não é áudio (um texto, foto, figurinha ou aviso) ou acabarem. Tocar num áudio do meio toca ele e só os de baixo. Enquanto um toca, o próximo já é baixado e aberto, para não haver pausa. Áudio que o aparelho não toca (formato sem suporte) é pulado; pausar interrompe a sequência. No iPhone o Safari pode exigir um toque para cada áudio (limite do navegador); no Chrome do Android encadeia direto. Teste: `tests/e2e/audio-sequencia.test.mjs`.

**Tela inicial na hora (`snapshot.js`):** antes, ao abrir ou atualizar o site, a lista aparecia vazia ("Carregando conversas…" e "Ninguém por aqui ainda") por ~1 s, e a foto de perfil e os pontos vermelhos chegavam depois, porque tudo esperava uma cadeia de consultas (perfil, chaves, aparelho, conversas). Agora o aparelho guarda uma "foto" da lista (`lacre:snap:<id>` no armazenamento do navegador: nomes, horário e não lidas de até 40 conversas, miniaturas 96×96 das fotos, a foto de perfil e os dois pontos vermelhos) e a **pinta no primeiro instante**, antes de qualquer consulta. Os dados de verdade entram em seguida e trocam sem piscar: as miniaturas guardadas também valem na lista nova (a foto inteira só substitui depois), e enquanto as conversas reais não chegam a lista da última vez não é trocada por uma vazia. Sem foto guardada (primeiro acesso no aparelho), só some o aviso "Ninguém por aqui" enquanto carrega. A foto é guardada de novo a cada mudança da lista (e ao fechar/recarregar a página), é apagada ao sair da conta e **nunca é confiada**: o que vem do armazenamento só passa se tiver a forma esperada (ids, tamanhos, miniatura só como `data:image/jpeg|png|webp` pequena) e entra na tela por `textContent`, nunca como HTML. Testes: `tests/snapshot.test.mjs` e `tests/e2e/inicio-rapido.test.mjs` (servidor lento de 4 s: lista, não lida, foto e ponto já na tela em menos de 1,5 s, sem a lista ficar vazia na troca).

**A tela não "balança" ao rolar logo depois de abrir (achado num vídeo do celular):** (1) mensagem que o servidor acrescenta depois só leva a tela ao fim se a pessoa já estava perto do fim (ou se foi ela que enviou); (2) o botão "Salvar figurinha" já ocupa o lugar dele (invisível) e o espaço da figurinha usa a proporção real, então a lista não muda de altura quando a imagem termina de carregar (antes cada figurinha recebida crescia ~30 px, quadro a quadro, enquanto se rolava). Testes: `tests/e2e/rolagem.test.mjs`.

**O servidor só confere e NUNCA refaz a lista** (a 1ª versão refazia quando achava uma linha mais antiga que a mais nova pintada, e como as conversas reais têm linhas que não viram balão, a lista aparecia, sumia por 1 s e voltava): o que já está na tela só atualiza "vista" (minhas) e "lida" (recebidas); linhas que o aparelho já decifrou (`conhecidos`: mensagens, reações, toques) não são relidas; o que ainda não era conhecido (chegou com o app fechado) é decifrado e entra no fim, ou, se for mais antigo que a mais nova pintada, **no lugar certo pela hora** (`posicionarPelaHora`; em grupo `ajustarAutores` refaz o nome e a foto da sequência). Mensagens que chegam durante a abertura esperam na fila e entram no fim, uma vez só. Testes: `tests/e2e/abrir-rapido.test.mjs` (servidor atrasado em 5 s: a lista já está na tela, no fim e com os chips; um vigia confere que **nenhuma mensagem é apagada da tela nem a lista volta a ficar escondida** quando o servidor responde, o que reproduz o defeito da 1ª versão).

## Trocar o nome de usuário
Em **Perfil → Trocar nome de usuário**. Regras (todas conferidas no banco, na função `trocar_nome()`; o app só mostra as mensagens):
- o nome novo segue o formato do cadastro (3 a 20 letras minúsculas sem acento, números ou `_`; maiúsculas e `@` são limpos);
- **nunca um nome que já existe**, nem o nome antigo de outra pessoa que ainda esteja reservado (vale também para quem cria conta nova);
- **uma troca a cada 30 dias**; o banco devolve a data em que libera e a tela mostra;
- o **nome antigo fica reservado por 30 dias** (tabela `nomes_antigos`, que ninguém lê nem escreve direto): ninguém o pega para se passar pela pessoa, e ela mesma pode voltar a ele.
A conversa não depende do nome (tudo é ligado ao id da conta), então mensagens, grupos, chaves e o código de segurança continuam. **Aviso aos contatos:** logo depois de trocar, o Lacre manda um toque cifrado (sem conteúdo) a cada contato e participante de grupo, que atualizam o nome na hora; quem estava com o Lacre fechado vê a troca ao abrir. Na conversa (a dois ou em grupo) aparece, no lugar certo da linha do tempo, "@antigo agora é @novo", e o aviso continua depois de recarregar. Citações antigas (`@antigo`) continuam como foram escritas, mas deixam de ficar em destaque (o destaque vale para os nomes de agora). `usuario.js` tem a validação e os prazos, com testes.

## Cor e foto de cada pessoa nas conversas de grupo
- **Foto ao lado:** em grupo, a foto de perfil de quem escreveu aparece ao lado da **última** mensagem de cada sequência da mesma pessoa (quem não tem foto aparece com a inicial num círculo da sua cor). O nome continua só na primeira mensagem da sequência.
- **Balão colorido por pessoa:** o balão e o nome de cada pessoa têm a cor dela; as **suas** mensagens continuam azul-escuras. Há versão para o modo escuro (`cores.js`).
- **Cada pessoa escolhe a sua cor, por grupo:** em **Dados do grupo → Minha cor neste grupo**, uma folha com 10 cores prontas e a prévia de como o grupo vê você. As cores que outras pessoas já usam aparecem apagadas com a **foto de quem usa** (não uma letra, que poderia repetir).
- **Nunca a mesma cor de outra pessoa:** o banco tem um índice único `(grupo, cor)`; se duas pessoas escolhem a mesma ao mesmo tempo, a segunda recebe "essa cor acabou de ser escolhida". Quem entra num grupo ganha a primeira cor pronta livre; quem sai libera a sua. Grupos que já existiam receberam cores pela ordem de entrada.
- **Cor aleatória:** quando as 10 prontas estão em uso, aparece o botão "Cor aleatória (a mais diferente)". O aparelho testa mais de 200 candidatas e escolhe a que fica **mais longe da mais parecida** entre as cores em uso (distância CIE Lab entre as cores fortes, sem nunca repetir uma existente). O banco guarda só `#rrggbb`.
- **Segurança da cor:** uma cor recebida de outra pessoa nunca vai direto para a tela. O app usa só o **matiz** e fixa a luminosidade e a saturação (fundo claro, borda e nome legíveis, testados com preto, branco, amarelo etc.), então ninguém consegue mandar uma cor que deixe o texto ilegível. O formato (`p0`..`p9` ou `#rrggbb`) também é conferido no banco.
- **Limite:** acima de 10 pessoas as cores aleatórias ficam mais parecidas entre si; a foto e o nome continuam identificando quem escreveu.

**Estatísticas do grupo:** em "Dados do grupo" → "Estatísticas do grupo". Lista em ordem de quem mais falou (Hoje / Semana / Mês), com mensagens, tempo na tela e sequência de dias; tocar numa pessoa mostra tipos (texto, fotos, vídeos, áudios, figurinhas), respostas, citações (@) e "no grupo há". **Todos do grupo veem tudo, inclusive o tempo na tela**, e a tela avisa isso. Como é feito: (1) as mensagens são contadas **no aparelho** (`estatisticas.js`, a partir do histórico local; o servidor não lê nada), então o que chegou antes de a pessoa entrar ou com o Lacre fechado em outro aparelho pode faltar. Para os números baterem entre aparelhos, cada pessoa **publica no servidor só as contagens do que ela mesma enviou por dia** (`grupo_enviadas`, em `grupo_dia.env`, sem conteúdo; ao entrar/sair do chat do grupo e ao abrir as estatísticas) e quem lê usa o **maior valor de cada dia e tipo** entre a contagem local e a publicada (cada fonte só pode estar incompleta, nunca grande demais; "citada" é só local). É só exibição, não prova para moedas; reações não entram (não ficam no histórico). (2) O **tempo de tela** vem do servidor (`grupo_dia`, função `grupo_tela`): o app soma 5 s por vez só com o chat daquele grupo aberto, a aba visível e a pessoa mexendo nos últimos 60 s, e envia a cada ~60 s; o banco aceita no máximo 120 s por pedido, 6 h por dia, 4 pedidos por minuto, e só de quem está no grupo (dia de Brasília). `grupo_estatisticas` devolve os últimos 35 dias só a quem está no grupo. (3) **Base para moedas (sem regras ainda):** a tabela `moedas_extrato` (grupo, pessoa, quantidade, motivo, ref; única por motivo+ref para nunca pagar duas vezes) e `moedas_saldo`. Ninguém logado escreve no extrato: quando houver regras de ganho, elas entram por uma função do servidor. Importante para o futuro: o servidor só confere o que enxerga sem decifrar (mensagens por dia e tempo de tela); o tipo das mensagens só existe no aparelho e por isso não deve render moedas.**Estatísticas: o que o servidor confere (contra números forjados).** O app é código no aparelho de cada pessoa e qualquer membro pode falar com o banco por fora dele, então nenhum número que a pessoa *declara* vale por si. (1) **Tempo de tela:** `grupo_tela` só credita o tempo real que passou desde a última chamada da pessoa (um relógio só por pessoa, em qualquer grupo ou aparelho; sessão nova vale no máximo 70 s; teto de 6 h por dia). Pedir 120 s de uma vez só rende o tempo real. Ainda assim um script pode "ficar na tela" até o teto: tempo de tela não prova presença e não deve render moeda. (2) **O servidor conta sozinho** (`grupo_estatisticas`): `msgs` = envios da pessoa no grupo naquele dia (um envio = um lote de linhas com o mesmo horário, só `avisar=true`; reações entram, então é um máximo, nunca menos que o real) e `arquivos` = envios dela ao armazenamento no grupo (`<pessoa>/<grupo>/…`). (3) O que a pessoa publica sobre os próprios tipos (`grupo_enviadas`) fica guardado como veio, mas **ao exibir é limitado** (`limitar`, em `estatisticas.js`): fotos+vídeos+áudios ≤ `arquivos`; texto+fotos+vídeos+áudios+figurinhas ≤ `msgs`; respostas e citações ≤ `msgs`. Quem publica 5000 aparece com o que o servidor viu (teste: `tests/e2e/estatisticas.test.mjs`). Sobra: trocar um tipo por outro dentro do que realmente enviou, e gerar mensagens reais (visíveis ao grupo, no limite de 300/min). O **dia é sempre o de Brasília** (o mesmo do servidor). Para moedas, usar só `msgs`, a sequência de dias e tetos diários, com moedas por grupo e sem transferência.

**Selos (a moeda do grupo).** Em "Dados do grupo" → "Selos": saldo de cada pessoa e as regras. O ícone é o selo de cera (símbolo `#selo` em `index.html`). **O admin** (só o admin; sub-admin não) define como se ganha, numa tela de frases com números sublinhados que se tocam e abrem uma folha (−, digitar, +, atalhos): *entrar no grupo* (uma vez), *dia ativo* (mínimo de mensagens no dia), *mensagens enviadas* (a cada N), *arquivos enviados* (a cada N), *sequência de dias* (lista de marcos: N dias seguidos → Selos, cada marco paga uma vez por sequência) e um *limite de Selos por dia* opcional (desligado = sem limite). Cada grupo começa com tudo desligado. Valores de 1 a 999 (dias de 1 a 365, até 10 marcos). Só entram ações que o servidor consegue **conferir** (envios e arquivos que ele vê, datas): tempo na tela, tipo de mensagem, respostas e citações não dão Selos porque podem ser forjados. **Como funciona no banco:** `selo_regras` (um JSON validado por `selo_limpa`; o servidor guarda "desde" quando cada regra foi ligada, então nada é retroativo), `selo_ganhos` (o que alguém ganha num dia), `selo_apurar` (calcula os ganhos dos dias, **inclusive o de hoje**, e grava no `moedas_extrato` com chave única por pessoa+motivo+referência: rodar de novo não paga em dobro; as linhas do dia só crescem, ficam com o maior valor e nunca são tiradas; é feito sob demanda, sem tarefa agendada, quando alguém vê o saldo e antes de qualquer mudança de regra), `selo_saldo` (soma do extrato: **os Selos valem na hora**, sem "a confirmar"; a coluna `pendentes` fica sempre 0 só para o site antigo não quebrar), `selo_regras_ver`, `selo_regras_mudar` (só admin), `selos_resumo` (para o aviso). Ninguém logado escreve em nenhuma tabela; as funções internas não são chamáveis. **Aviso no chat:** cada mudança aparece como "@fulano mudou as regras dos Selos" (comparando `atualizado_em` com o que o aparelho já viu, como nas outras mudanças do grupo). Os Selos valem só no grupo e não são transferíveis. Mudanças valem na hora (para testes; depois vale um aviso prévio). Uma regra mais generosa no meio do dia sobe o ganho do dia inteiro; uma mais dura nunca tira o que já foi ganho. A loja de preços ainda não existe (aparece "em breve"). Módulo puro com testes: `selos.js`.
